## Context

`clink --serve` gives every client every link. The associative client of
link-foundation/ui#101 keeps only the links its user may read, so the server
must know who asks and what they may do. Deep-foundation keeps its
permissions as links (`Rule`, `RuleSubject`, `RuleObject`, `RuleAction`,
`Selector`); this issue does the same on doublets.

## Goal

An optional decorator over `ILinks` that hides the links a subject may not
read and refuses the writes it may not make, with the rules stored as links,
in the same links file or in a separate one, as configured.

## In scope

1. Rules as links: a pair `(g: Subject Object)` marked `(r: AllowRead g)` or
   `(r: AllowWrite g)`. A rule applies to a subject that is `Subject` or of
   type `Subject`, and to the links of type `Object` (its values and
   sub-types, see {{L01}}). The marker `Anything` matches every subject or
   every link. Write implies read.
2. `PermissionsDecorator(links, rules, subject)`: `Each`/`Count` skip what
   the subject may not read (a hidden link is as missing as a deleted one);
   `Create`/`Update`/`Delete` throw a `Forbidden` error and change nothing.
   An update needs the right to write the link before and after.
3. A new link is its creator's while it has no type (its source is 0), so a
   subject can create a link and then type it.
4. References and rollbacks are checked in the storage below the view, so a
   subject may reference a type it may not read (decide whether that should
   instead need a rule of its own: see link-foundation/ui's issue about
   hiding the existence of unreadable links).
5. Configuration: `--permissions <file>` (rules in a separate links file) or
   `--permissions self` (rules in the data); without it, nothing changes.
6. Server: `(auth: token)` → `(subject: i)`; every later request of the
   connection runs as that subject. Authentication is pluggable (a token
   table as links, or an external callback in the library).

## Out of scope

Subscriptions ({{L03}}), triplets ({{L04}}).

## Step-by-step plan

1. Port `packages/ui-links/src/permissions.js` and its tests to C# and Rust.
2. Add the server session subject and `(auth: …)`.
3. Add the CLI options and README documentation.
4. Replay the permission tests of `packages/ui-links/tests/server.test.js`.

## Acceptance criteria

- With rules "User writes Note, User reads Public", a user sees the notes and
  the public links only, and `(update: …)` of a link of another type answers
  `(error: 'Forbidden: update N')` with the store unchanged.
- A failed request is undone completely, even when part of it touched links
  the subject cannot see.
- Rules in a separate file work the same as rules in the data.
- Without `--permissions`, every existing test passes unchanged.
