## Context

`withPermissions` checks references (and undoes failed requests) in the
storage below the permission view, so a subject can type its links as a type
it may not read (alice may write notes without reading the link of the type
`Note`). The price: a subject can learn that an address exists by
referencing it, because a missing address answers `Link not found` and an
unreadable one does not (see "Permissions" and "The links server" in
`packages/ui-links/README.md`). deep-foundation checks inserts against the
type of the new link (`AllowInsert` on `type.can_object`).

## Goal

A documented decision, and, if chosen, a rule `AllowReference` (or reuse of
`AllowWrite` on the type) that a reference needs, so an unreadable link is
indistinguishable from a missing one for subjects without it.

## In scope

1. Compare: keep the leak; require read; require a new `AllowReference`
   rule; answer `Link not found` for both.
2. Implement the chosen option behind the policy, with tests for both kinds
   of subject.
3. Bring the decision to link-cli's permission layer ({{L02}}).

## Acceptance criteria

- A test shows that a subject without the right gets the same error for an
  unreadable and for a missing address.
- The examples still run.
