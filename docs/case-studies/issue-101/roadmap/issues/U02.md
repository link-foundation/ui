## Context

`createSqlLinks(db)` stores links in any database with `exec` and `prepare`
(Node.js' `node:sqlite`, Deno, Bun, better-sqlite3). In the browser the
persistent storages today are IndexedDB and `localStorage` through
`persistLinks`, which keep the whole store in memory. The issue asks also
for "database on top of sqlite in the browser".

## Goal

A browser SQLite storage with the same interface, so an application can keep
more links than fit in memory.

## In scope

1. An adapter from the official `@sqlite.org/sqlite-wasm` (OO1 API,
   Apache-2.0/public domain) to the `exec`/`prepare` shape `createSqlLinks`
   takes, or a small `createSqliteWasmLinks(db)`.
2. Persistence on OPFS (`opfs` or `opfs-sahpool` VFS) in a worker; the
   asynchronous boundary hidden behind a synchronous cache or exposed as an
   asynchronous storage, decided and documented in the pull request.
3. The shared storage tests (`packages/ui-links/tests/storages.test.js`) run
   against it in a browser (Playwright).

## Out of scope

`wa-sqlite` or `absurd-sql` (see the library survey of the issue 101 case
study for why sqlite-wasm is first).

## Acceptance criteria

- The shared storage tests pass in Chromium and Firefox.
- Links written in one page load are read in the next.
