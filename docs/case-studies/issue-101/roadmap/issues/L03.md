## Context

A client that keeps a partial copy of the links (a "minilinks" or
"minimongo") must learn when other clients change the links it holds.
`clink --serve` answers requests only. link-foundation/ui's `ui-links`
server adds three operations; this issue makes them part of link-cli's
protocol so the same clients work against `clink --serve`.

## Goal

Subscriptions in `LinksServer` (C# and Rust), framed like every other reply.

## In scope

1. `(subscribe: (i s t))` → `(subscription: n)`; the restriction is a link
   pattern as in `(each: …)`.
2. Later, when another connection changes a matching link, the server pushes
   `(notify: n)` followed by the changes as `(before) (after)` lines, to that
   connection only. With the permission layer ({{L02}}), the subscriber sees
   only what it may read: a link that becomes unreadable arrives as a
   deletion.
3. `(unsubscribe: n)` → nothing; closing the connection drops its
   subscriptions.
4. `RemoteLinks` and the JavaScript client `@link-foundation/link-cli-client`
   tell pushes from replies (a push starts with `(notify: …)`).
5. Document the operations in `docs/protocol/` with a recorded conversation
   that both ports replay.

## Out of scope

WebSocket framing (link-cli#30), GraphQL subscriptions ({{L06}}).

## Acceptance criteria

- Two connections: the first subscribes to `(* * *)`, the second creates a
  link; the first receives `(notify: 1)` and `() ((1: 0 0))` without asking.
- After `(unsubscribe: 1)` nothing more is pushed.
- C# and Rust replay the same recorded conversation.
