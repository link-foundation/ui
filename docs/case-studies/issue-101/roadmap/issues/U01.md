## Context

`@link-foundation/ui-links` has two transports for its synced client:
`connectInProcess(server)` and `connectLinks('host:port')` over TCP
(`@link-foundation/ui-links/tcp`, Node.js only). A browser cannot open a TCP
socket, so a link-ui application in the browser cannot reach a links server
yet. link-cli plans a WebSocket mode for its server in
link-foundation/link-cli#30.

## Goal

A transport `connectWebSocket(url, { binary? })` for browsers (and Node.js,
Deno and Bun, which have `WebSocket`), and `listenLinksWebSocket(server,
options)` for the Node.js server.

## In scope

1. One message per request and per reply; pushes start with `(notify: n)`,
   as over TCP.
2. Text frames carry Links Notation text; binary frames carry the binary
   codec of `links-notation` (`encodeBinary`/`decodeBinary`).
3. Requests answered in order; a closed socket rejects the waiting requests
   with `offline`, and the synced client keeps its outbox (see {{U05}}).
4. The server side with a small permissive WebSocket library (`ws`, MIT) or
   the runtime's own server where there is one; decide in the pull request.
5. Follow the framing link-cli chooses in link-foundation/link-cli#30, or
   propose it there.

## Acceptance criteria

- `examples/ui-links-tcp.mjs` has a WebSocket twin that runs in CI.
- A Playwright test opens a page that syncs two tabs through the server.
- Text and binary frames give the same results.
